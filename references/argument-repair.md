# 修复论证中缺失的一环

先区分“修错”与“提升解释”。事实完整、专家能从全文拼出答案，只能说明材料可用；不能据此判断入口已经通俗。局部修错按原范围处理。用户要求明显包装增量时，找出一处读者仍需自行补出的连接，例如约束如何迫使设计选择、多个部件为何共同必要、验证工作排除了哪种替代解释。

先判断问题属于主次失衡还是事实缺失。主次失衡时，先按[入口分工](novelty-framing.md)重排、压缩或移位，再写实际对照；不要默认再加一条解释链。保留事实与必要条件，不保留原句顺序。候选可以从实际改变起笔，或从最能区分方案的证据起笔；比较相同事实下哪个入口更集中，而不是哪版覆盖的术语更多。

例如“系统使用ID、代际号和校验和”信息齐全但关系仍隐含。先让读者看到旧任务迟到、槽位已换主人的具体情形，再解释三项检查分别防止什么。保留必要数字、失败记录与机制条件；简洁应减少读者来回拼接，不以删除有用证据或最少字数为目标。

| 原问题 | 修改方法 | 复查重点 |
|---|---|---|
| 收益未说明基线 | 在数字旁写明比较配置和共同条件 | 增量比较不会被读成与最初系统的比较 |
| 只列实现步骤 | 用执行顺序说明防止的错误或增加的能力 | 正确性和容量没有被写成测量性能 |
| 重复报结果，没有设计含义 | 说明成功与反例支持哪项选择 | 失败案例保留，未测原因不作定论 |
| 必要条件散落多处 | 完整定义一次，在影响结论处使用同一名称 | 局部可读而不过度重复 |
| 贡献混合机制、验证和发现 | 分清各自作用，围绕同一主线组织 | 不把一项实现拆成多个新算法 |
| 续改后邻段重复 | 将完整原因放在一个位置，邻段只讲独有条件或结果 | 删除的是重复解释，不是独有事实 |
| 短句改变证据强度 | 写回具体观察和比较对象 | 活动计数不是安全性证明，相对变化之比不是绝对效率 |

沿着[全文对应表](../templates/argument-map.md)追踪一个重要主张，从前部到定义、必要条件、验证和结果，再反向检查重要发现是否进入结论。不是每个结果都需要成为新贡献。

关键比较应记录数量、分子或基线、分母或候选、样本和设置、汇总方式、来源。正文保留避免误读所需的字段，完整配置和哈希放入复现材料。资源增量和性能增量可能使用不同基线，应分别核对。

已有百分数也要复算。若算术有误，保留测量输入、只修正派生值，明确公式和数值修改例外；不能用“数字未变”掩盖已知错误。

接受请求数、消费值数、局部避免的等待、完整程序周期减少可能不同。查计数定义和匹配记录，保留合理残差；不要强行凑齐，也不要编造残差原因。零值是观察，具备条件不等于推荐使用，运行活动不等于正确性证明。

方法段让设计决定和作用连起来，结果段让证据回答设计问题。新增查表或复现细节可能必要，但单独列作可复现性修正；没有改变创新、困难、工作与证据的理解顺序时，不记为叙事提升。经验选择不写成最优选择，未知失败原因继续待定。

审阅者先看候选作品再看修改理由，比较相同范围的父稿，检查改善和代价。全文记录各节“修复、保留及理由、依赖来源”；该记录不自动证明逐句阅读或写作质量。已知缺陷复查不是新的盲读。“无需再改”必须区别于“尚未检查”。

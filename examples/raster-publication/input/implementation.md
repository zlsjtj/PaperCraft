# Implementation notes (DEMO internal sources)

[I1] Existing rendering service, before any transfer changes: a root is an array of 64 tile-version pointers. Each tile has 4096 four-byte cells, so a full raster payload is 1,048,576 bytes. A tile version is immutable after publication. The producer already publishes a new root atomically for local readers. Copying roots, reference counting, sparse invalidation and tile checksums predate the study. The client renderer already captures one published root at the start of a frame. None of these operations is being proposed as a new primitive.

[I2] Protocol labels are implementation names, not novelty categories. FS = full snapshot, stage one complete raster, validate all packets, then switch visible root. IT = transfer changed tiles with a revision tag and install each received pointer immediately. SP = changed-tile patch from an explicitly named base revision to a target revision; the client pins its visible base, stores replacements in a private pending root, then publishes that root only after all declared changed tiles have arrived and validated. FS and SP both use the pre-existing root swap. IT messages also have the target revision tag; a tag alone does not prevent its visible root from containing tile versions chosen from different roots. A late valid message must not update a newer visible root.

[I3] A patch manifest identifies base, target, and changed-tile set. Unchanged tile versions may be shared from the named base. Target coherence means matching the producer's target root, not giving every tile a newly incremented creation timestamp. For example target r=11 may legitimately keep an unchanged tile created in r=8. Pending roots are not exposed; display reads do not wait for pending network packets. There is no asynchronous claim that all remote clients display the same revision at the same wall-clock instant.

[I4] The server retains a chain of manifests for at most 8 completed revisions in this DEMO configuration. The client acknowledges only the root it has published. Patches are derived against that acknowledged revision when available. To coalesce several manifest steps, take the union of touched coordinates and transmit their values from the target root; do not transmit an intermediate value just because its manifest came first. If a tile changes and later returns to its old bytes, it can remain in the union; the protocol is correct but is not a minimal-difference compressor. No longer history is claimed.

[I5] If acknowledged base is unavailable, wrong, or unverifiable, request FS. Incomplete or invalid pending patches are discarded; visible root stays at the last coherent revision. Duplicate matching packets are idempotent; conflicting duplicates cause patch rejection. Out-of-order data may be staged under the named target, but a commit is checked against the pinned base before publication. Disconnect discards uncommitted pending state. A corrupted patch does not create a partially visible root. This is volatile display state, not a crash-recovery database or durable transaction protocol.

[I6] A root pointer table is 512 bytes in this configuration and descriptors/reference counters add 4096 bytes per pending update. An SP update retains old tiles plus replacements until display readers release their old root; FS similarly retains an old visible frame and a new full frame. Max pending payload for SP can reach a full frame in dense changes. Old-reader pinning has no proven bounded lifetime in this DEMO; retained memory numbers in the result table assume a single reader finishes within one measured display cycle. Do not generalize them to stalled readers. Manifest validation and root assembly consume CPU time and can outweigh savings.

[I7] Debug event sequence for a two-tile illustration within the 64-tile system: visible base r=10 contains tile A version a0 and tile B version b0. Producer root r=11 needs a1 and b1. IT receives a1 then delays b1; the visible pair (a1,b0) is neither r=10 nor r=11. SP retains (a0,b0) while a1 is pending; when both target replacements validate, the next reader sees (a1,b1). An unchanged tile C shared from r=10 stays identical in both views. This sequence illustrates the check, not a new timing measurement.
